# ModAgent Pro 发放、授权与抗破解设计

## 目标与安全边界

本方案的目标是阻止普通复制、控制订阅权益、支持设备撤销与泄露追踪，并让篡改后的客户端无法继续使用更新和服务端能力。

任何完全运行在用户电脑上的程序都无法保证“绝对不会被破解”。本项目不承诺不可破解，而是通过签名授权、短期凭证、服务端能力和分层校验提高破解与持续维护成本，同时保证误判或订阅到期不会删除用户数据。

## 发行通道

发行物分为互不覆盖的两个通道：

| 通道 | 应用身份 | 数据目录 | 更新通道 | 用途 |
| --- | --- | --- | --- | --- |
| Pro Stable | ModAgent Pro | `.modagent` | `subscription` | 已订阅用户 |
| Pro Beta | ModAgent Pro Beta | `.modagent-beta` | `subscription-beta` | 邀请制测试 |

下载文件放在私有对象存储中。用户登录账户中心后，服务端检查权益并签发 5–15 分钟有效的下载 URL。不要把永久下载地址或共享网盘直链作为正式发放方式。

每个发行版本同时发布：

- Windows 代码签名后的安装程序和主程序；
- SHA-256 文件摘要；
- 由独立发布密钥签名的更新清单；
- 版本、通道、最低服务端协议版本和撤回状态。

## 购买与发放流程

1. 支付平台 webhook 把订单写入订单表，重复 webhook 通过平台订单号保持幂等。
2. 后端创建或续期 entitlement，不直接生成一个永久通用激活码。
3. 用户登录账户中心，可以下载对应通道并查看设备占用。
4. 退款、拒付或订阅终止后，停止签发新的短期授权；已有凭证在有效期或宽限期结束后失效。
5. 客服可以撤销单个设备、整个权益或某个有问题的发行版本，所有操作进入审计日志。

## 激活协议

首次启动时，客户端生成随机安装标识和设备密钥对。优先使用安装密钥，不采集硬盘序列号、主板号等侵入式硬件指纹。

客户端向服务端发送：

- 登录会话或一次性激活码；
- 安装公钥及其摘要；
- 应用版本、edition 和 channel；
- 随机 nonce。

服务端检查订阅、设备上限、通道和版本策略后，返回签名 entitlement token。建议使用 Ed25519 或 P-256，服务端私钥保存在 KMS/HSM；客户端只内置公钥，绝不内置可以签发授权的共享密钥。

建议 token 至少包含：

```json
{
  "iss": "modagent-entitlement",
  "sub": "pseudonymous-user-id",
  "entitlement_id": "ent_xxx",
  "device_key_hash": "sha256:...",
  "edition": "subscription",
  "channel": "beta",
  "features": ["pro"],
  "iat": 0,
  "nbf": 0,
  "exp": 0,
  "grace_until": 0,
  "min_version": "1.3.0",
  "jti": "unique-token-id",
  "kid": "signing-key-id"
}
```

客户端验证签名、设备公钥摘要、edition、channel、时间窗口和版本策略。token 通过 Electron `safeStorage`/Windows DPAPI 保存。在线时定期刷新，建议在线凭证有效 3–7 天，另给 7 天宽限期，避免短时断网影响正常使用。

订阅过期或授权被撤销时，只停用 Pro 能力和在线服务。已有数据必须保持可读、可导出、可卸载，禁止自动删除用户数据或“自毁”安装。

## 校验位置

不能只在界面里保存一个 `isPro` 布尔值。授权应在能力边界重复校验：

- Electron 主进程启动和 IPC；
- Python 后端的 Pro API；
- 下载、更新、云端规则和其他服务端接口；
- Beta 专属通道和诊断上传。

本地后端只接受由主进程传入的短期会话证明，并校验端口绑定和随机启动密钥。真正有价值且可以联网提供的能力应在服务端再次校验 entitlement，避免修改一处前端判断就解锁全部能力。

## 抗破解与泄露追踪

必须做：

- 对安装包、可执行文件和更新清单签名；
- 对下载使用短期签名 URL；
- 对授权使用非对称签名和短期有效期；
- 限制设备数量，并提供用户自助解绑；
- 记录 token 重放、异常设备数、异常下载频率和版本；
- 支持按用户、设备、token、发行版本撤销；
- 签名密钥带 `kid`，支持轮换和短期双钥过渡。

建议做：

- 给每位测试者分配 tester ID，在“关于”和诊断包中显示；
- 在下载清单或安装包旁车元数据中写入不可猜测的发放 ID，用于定位泄露来源；
- 对高价值规则或内容按用户授权在线下发；
- 对关键校验做多点、不同层次实现，使简单补丁难以长期维护；
- 对 JavaScript/Python 打包产物做适度混淆，但只把它视为延缓手段。

不建议做：

- 依赖一个全局共享注册码；
- 在客户端内置私钥或对称“授权密钥”；
- 依赖机器码强绑定且不给解绑；
- 使用驱动、反调试、破坏系统或删除数据的激进手段；
- 把壳或混淆宣传为不可破解。

## 最小服务端模型

建议至少包含以下实体：

- `users`
- `orders`
- `entitlements`
- `devices`
- `activations`
- `issued_tokens`
- `revocations`
- `releases`
- `download_grants`
- `audit_events`

最小接口：

- `POST /v1/payments/webhook/{provider}`
- `POST /v1/activations`
- `POST /v1/entitlements/refresh`
- `DELETE /v1/devices/{id}`
- `GET /v1/releases/latest?channel=...`
- `POST /v1/releases/{id}/download-grant`
- `GET /v1/revocations`

服务端可使用 FastAPI + PostgreSQL；发行物使用 S3/R2 类私有对象存储和 CDN；签名私钥使用云 KMS。账户登录建议采用成熟身份服务或邮箱一次性链接，避免自行保存密码。

## 分阶段实施

### P0：公测前

- 购买 Windows 代码签名证书并接入构建；
- 使用独立 Beta 身份、数据目录和更新通道；
- 为测试者创建独立邀请码、到期时间和最多 1–2 台设备；
- 给每份发放记录生成 tester ID 和短期下载地址；
- 公测到期只锁定 Beta 功能，保留导出和卸载。

### P1：付费上线前

- 完成订单 webhook、账户、entitlement、设备管理和撤销；
- 接入非对称签名短期 token；
- 在 Electron、后端和下载/更新服务三层校验；
- 建立签名发行清单、密钥轮换和审计告警。

### P2：规模化后

- 增加异常检测、token 重放检测和自动限速；
- 把高价值在线能力迁移到授权 API；
- 增加客服后台、用户自助解绑和泄露处置流程；
- 定期进行发布密钥、支付 webhook 和授权绕过的安全测试。

## 当前代码状态

当前代码已经完成 Beta 与 Stable 的应用身份、可执行文件名、数据目录、安装卸载逻辑和更新通道隔离，也已经把同一游戏的多个安装实例按路径生成稳定 `game_instance_id`。

当前 `subscription` 构建身份仍然只代表“这是 Pro 构建”，不代表“当前用户拥有有效订阅”。上述服务端 entitlement、设备激活和能力边界校验仍需作为下一阶段实现，不能用构建 edition 代替真实授权。

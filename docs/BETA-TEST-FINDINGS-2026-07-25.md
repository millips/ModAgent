## BT-UPDATE-01：已安装 Mod 身份推断错误

- 严重级别：P0（错误更新对象可能覆盖用户文件）
- 用户意图：更新当前已安装的 `Auto Forager`。
- 搜索候选：
  - Nexus #7736：`Auto Forager (previously Auto Shaker)`
  - Nexus #47161：`AutoForager`
- 本机事实：测试用户确认实际安装来源是 **Nexus #7736**。
- 错误表现：Agent 根据名称、作者/日志线索推测安装项更像 #47161，并要求用户二选一；该推测与本机事实不符。
- 初步原因：
  1. 本地数据库使用 `local_*` 哈希身份，未保存或未恢复可靠的 Nexus 来源绑定。
  2. 两个候选名称高度相似，名称模糊匹配不能证明来源身份。
  3. SMAPI `manifest.json` 的 `UniqueID`、作者、版本没有与 Nexus 详情形成确定映射。
  4. 当前对话层可能把日志/分类线索当成来源证明。
- 安全要求：
  - 无稳定来源绑定时不得宣布“安装的是某个 Nexus ID”。
  - 更新前必须以本地 manifest、历史安装账本、已验证来源绑定或包内指纹完成身份确认。
  - 两个候选均可能匹配时只能报告“身份未确认”，不得用作者/名称近似度替代证明。
  - 用户明确提供 Nexus ID 后，应写入经过确认的手动绑定，并在后续更新中复用。
- 验收条件：
  - 给定本地 #7736 的 manifest/文件指纹，更新检查稳定选中 #7736。
  - #47161 即使名称更接近，也不能覆盖已有的确定绑定。
  - 身份未确认时更新按钮不可执行，只允许查看候选和补充绑定。

## BT-UPDATE-03：Stardew Valley 更新错误落入 BepInEx

- 严重级别：P0（更新后 Mod 实际失效，禁止按当前候选发行）
- 已确认现场：
  - `Mods/AutoForager自动觅食` 只剩 `i18n/`，没有主 DLL；
  - `BepInEx/plugins/7736_Auto_Forager_(previously_Auto_Shaker_)` 包含 `AutoForager.dll` 和 `i18n/`；
  - Stardew Valley 使用 SMAPI，只加载游戏根目录下的 `Mods/`，不会从该 BepInEx 路径加载此 Mod。
- 已确认代码根因：
  1. `installer.GAME_LAYOUTS` 没有 `stardewvalley`；
  2. Stardew 专项代码目前只覆盖 SMAPI 状态验收和压缩包依赖预检，没有定义安装落位；
  3. `mod_update` 卸载旧版后直接调用通用 `installer.install_mod(...)`；
  4. 通用安装器把未匹配的散 DLL 兜底到 `BepInEx/plugins/<包名>/`。
- 当前测试机处置：
  - 对“卸载两个残留并重新下载”的确认问题选择 **n**；
  - 当前版本重新下载后仍会走同一错误落位，不能解决问题；
  - 保留现场或先备份，待修复版使用 SMAPI 专项迁移/修复流程。
- 必须实施：
  - 增加 Stardew/SMAPI 安装布局：完整 Mod 文件夹必须落入 `Mods/<mod-folder>/`；
  - 以 `manifest.json` 作为 SMAPI Mod 根目录的强证据，保持 DLL、`i18n/`、内容包及其他同级文件在同一目录；
  - 禁止 Stardew 的普通 Mod 使用 BepInEx 散 DLL 兜底；
  - `mod_update` 安装后必须调用 `stardew_smapi_status` 或等价本地验收，确认目标 manifest 与 DLL 位于 `Mods/`；
  - 更新失败或落位错误时必须恢复旧版本，不能只以“文件已复制”判定成功；
  - 增加从错误 `BepInEx/plugins/...` 路径迁回 `Mods/` 的一次性修复流程，并同步数据库绝对路径。
- 回归用例：
  - #7736 更新包包含 `manifest.json`、`AutoForager.dll`、`i18n/` 时，三者必须落在同一个 `Mods/<folder>/`；
  - 更新完成后 `BepInEx/plugins/` 不得新增 #7736 文件；
  - SMAPI manifest 扫描必须能识别更新后的 UniqueID 与版本；
  - 旧目录清理、数据库 `files_installed`、卸载预览和快照均指向新路径。

## BT-I18N-01：Mod 管理界面缺少中文名与中文简介

- 严重级别：P1（可用性）
- 当前表现：管理页主要显示英文 Mod 名，第二行仅显示内部 ID；普通中文用户无法快速理解用途。
- 已确认实现缺口：前端已经预留 `name_cn` 和 `desc` 展示位，但 `/mods` 接口没有返回对应元数据，前端目前把 `name_cn` 设成英文原名、把 `desc` 固定成内部 ID。
- 目标展示：
  - 主标题：中文参考名；
  - 副标题：来源英文原名；
  - 简介：基于来源详情、manifest 或 README 的中文功能简介；
  - 身份：来源平台与稳定 ID 单独显示，不能被中文名替代。
- 数据原则：
  - 中文名只是显示别名，不参与下载、更新、卸载和依赖匹配。
  - 没有详情证据时不根据标题猜功能；显示“简介待核验”。
  - 翻译结果需要持久化，避免每次打开管理页重复调用模型或产生不同译名。

## BT-FOLDER-01：物理 Mod 文件夹中文化

- 严重级别：P1（需要安全设计，不能直接照搬手工改名）
- 测试者效果：例如 `AutoForager自动觅食`，在资源管理器中可读性很好。
- 当前风险：
  - `installed_mods.files_installed` 保存绝对路径，外部重命名会使账本失效；
  - 更新可能在原始英文目录重新解压，形成两个同时加载的副本；
  - 卸载、禁用、依赖检查和快照可能漏掉改名后的文件；
  - 部分加载器、整合包或脚本可能依赖原目录结构。
- 当前决策：**不默认重命名现有真实 Mod 目录。**
- 推荐方案：
  1. 第一阶段先完成管理界面的中文名与中文简介，不改磁盘路径。
  2. 如需资源管理器可读性，设计“受管中文别名”功能：仅处理 ModAgent 新安装且通过加载器专项验证的目录。
  3. 重命名必须作为事务执行：更新数据库全部路径、来源绑定和快照域；失败自动回滚。
  4. 更新前用稳定 ID/manifest `UniqueID` 找目录，不再依赖文件夹名。
  5. 对现有用户手工改名目录先重新扫描并对账，不直接二次改名。

## 下一步所需证据

- 本轮 `mod_update_check` 的结构化结果。

- 若执行过来源对齐，保留 #7736 与 #47161 的评分、匹配方法及详情核验结果。

## BT-INTENT-03：生效性诊断错误转入 Mod 推荐

- 记录时间：2026-07-28
- 严重级别：P1（核心意图路由）
- 用户原话：`帮我看看现在有没有不生效的 没有安装依赖的模组`
- 实际流程：
  1. 正确调用了一次 `game_diagnose`；
  2. 随后连续调用多次 `nexus_search`；
  3. 最终输出“找到候选”和“执行计划”，内容为新 Mod 推荐，而不是已安装 Mod 的健康检查结论。
- 问题性质：用户要求的是**已安装 Mod 诊断**，不是搜索、推荐或安装。诊断结果不足时也应该说明缺少哪些本地证据，不能用外部搜索候选替代诊断。
- 正确流程：
  1. 获取已安装 Mod 清单与启用状态；
  2. 检查加载器、manifest、DLL、依赖关系和冲突；
  3. 读取游戏/加载器日志，判断未加载、报错、缺依赖和版本不兼容；
  4. 按“正常 / 疑似未生效 / 缺少依赖 / 无法确认”输出本机条目；
  5. 只有用户明确要求“帮我找替代品/缺失依赖下载地址”时，才允许进入来源搜索。
- 验收条件：
  - “检查不生效、缺依赖、报错、冲突”等诊断请求不得自动触发 `nexus_search`、`thunderstore_search` 或 `mod_recommend`。
  - 不生成推荐决策表和安装计划。
  - 必须明确列出已检查数量、异常数量、证据来源及无法确认项。
  - 若本机证据不足，应提示用户启动一次游戏或提供日志，而不是推荐新 Mod。

## BT-DIAG-04：诊断结论与处置建议需要实机复核

- 记录时间：2026-07-28
- 严重级别：P1（诊断可信度与安全处置）
- 用户目标：检查当前不生效、报错或缺依赖的已安装 Mod。
- ModAgent 本轮声称：
  - `clay_BetterMap` 因 `FieldAccessException` 不生效，推断为游戏更新后字段不可访问；
  - `YMC_MHZ_MoreHead` 与 `Xuaun_MoreHeadBridge` 因相同 `MissingMethodException` 不生效，推断为游戏更新后旧方法签名消失；
  - `MoreHeadBridge` 的硬依赖只有 BepInEx 与 REPOLib，依赖均已安装；
  - 其余 20 个 Mod“无报错”；
  - 建议禁用/卸载上述三个 Mod，或等待作者更新。
- 审核风险：
  1. 日志出现异常不等于该异常仍发生在最近一次启动；
  2. 单条异常不能直接排除重复 DLL、错误版本依赖、加载顺序或旧日志残留；
  3. “其余 20 个无报错”必须有本次启动边界和逐 Mod 加载证据，不能只靠未命中关键词；
  4. 禁用/卸载不是同一风险等级，诊断阶段应优先建议快照后禁用隔离测试，而不是直接卸载；
  5. 需要核对本地 Mod 版本、来源页当前兼容说明、依赖版本范围及是否存在同物理 Mod 的重复副本。
- 待独立实机复核：
  - 当前游戏路径、最新日志时间和本次启动边界；
  - 三个异常的完整堆栈、首次/末次出现时间和出现次数；
  - 本地 DLL/目录版本与来源绑定；
  - REPOLib、MoreHead/MenuLib 等实际依赖版本；
  - 最小化禁用测试顺序及可回滚方案。
- 2026-07-28 独立实机复核结果：
  - 游戏：R.E.P.O. `v0.4.4.3`；BepInEx `5.4.23.4`；本次启动加载 18 个插件。
  - `BetterMap 1.0.5`：插件成功进入 Chainloader，设置页可见，但本次启动连续 3 次出现
    `MissingMethodException: RoomVolume.SetExplored()`；本地 `BetterMap.dll` 确实引用该旧 API。
  - 用户实测：BetterMap 已启用，`Show Teammates`、`Show Enemies`、`Explore All Rooms`
    均为 ON，但游戏内功能不生效。可确认属于“加载成功但运行逻辑失效”。
  - `MoreHead 1.4.5`：本次启动成功加载 19 个装饰物，日志明确记录 UI 初始化完成。
  - `MoreHeadBridge 3.0.0`：日志明确记录 `19/19 registered, 0 error(s)`；用户实测
    MoreHead 可用。
  - 原诊断把 `MoreHeadBridge.PartShrinkerLogFilter:LogException` 当成异常归属证据是错误的：
    该类是全局日志过滤器，其他 Mod/游戏抛出的 Unity 异常也会经过它。
  - 本次最新日志不存在截图所述 `ValuableObject.Discover(...)` 或
    `MapCustom.mapCustomEntity` 异常；若它们来自上一次启动，也不能据此归责 MoreHead。
  - 当前真正遗漏的另一项异常为
    `REPOLib: Bundle lucy_item contains no mods!`，说明 `Lucy Figure 1.0.2`
    至少在本次启动未正常向 REPOLib 注册内容，需要单独复核。
  - REPOLib 当前实际加载 `4.2.0`；旧 `4.0.1` 副本存在，但 BepInEx 已明确跳过旧版，
    没有同时加载两个版本。
- 结论：
  - 原回答关于 BetterMap“不生效”的大方向正确，但具体异常与处置不完整。
  - 原回答关于 MoreHead 和 MoreHeadBridge“不生效”的结论错误。
  - “其余 20 个无报错”错误，至少漏掉 Lucy Figure 的 REPOLib 注册错误。
  - 直接建议卸载三个 Mod 不是最优解；应先采用可逆配置测试与精确兼容补丁。
- 推荐处置顺序：
  1. 保持 MoreHead 与 MoreHeadBridge 启用，不做卸载。
  2. 先关闭 BetterMap 的 `Explore All Rooms` 并保存、重启新关卡，确认
     `RoomVolume.SetExplored()` 是否消失以及队友/敌人标记是否恢复。
  3. 若标记仍失效，给 BetterMap `1.0.5` 安装明确适配 R.E.P.O. `v0.4x`
     的 `Zichen-ModsUp 1.0.5` 兼容补丁，再复测。
  4. 补丁仍失败时才快照后禁用 BetterMap；不要先卸载，以保留可回滚证据和配置。
  5. Lucy Figure 单独执行禁用对照或更新/重装验证，不与 BetterMap/MoreHead 混为一组。

## BT-DL-06：终止性下载错误被重复重试且流程不收尾

- 记录时间：2026-07-28
- 严重级别：P0（长时间无效等待、错误换源并造成“工具卡住”的观感）
- 现象：
  1. GitHub/直链返回 HTTP 404 后仍按临时网络故障重复 5 次；
  2. `download_from_url` 失败后 Agent 又改用 `mod_download` 或其他目标继续尝试；
  3. 界面已经显示失败，但总任务仍停在“完成，正在继续处理”。
- 根因：
  - 下载器只统计连续失败次数，没有区分终止性 HTTP 客户端错误与临时网络错误；
  - 工具层只返回一段通用错误字符串，Agent 无法可靠判断是否应该停止；
  - 同一轮只缓存成功下载，没有缓存已经确认的终止失败。
- 2026-07-28 修复：
  1. 404/410、401/403 及其他终止性 4xx 首次失败即停止；
  2. 408/425/429/5xx、断网和超时最多自动尝试 5 次；
  3. 返回结构化的 `failure_kind`、`retryable`、`attempts`、`http_status`、
     `automatic_retry_allowed` 与 `user_action`；
  4. 同一终止失败在本轮缓存，不再次联网；
  5. 明确指定的目标失败后，不允许在同一轮静默替换来源或 Mod ID；
  6. 收到 `stop_further_downloads=true` 且 `continue_other_items=false` 后，
     对话立即输出失败原因并结束本轮。
- 回归：
  - HTTP 404：1 次请求后终止；
  - HTTP 503/断网：5 次有界尝试后停止；
  - 同一终止失败：工具只执行 1 次；
  - 明确目标失败后换源：被 Agent 护栏拦截。

## BT-SNAPSHOT-07：快照实例 ID 被误判为跨游戏

- 记录时间：2026-07-29
- 严重级别：P1（快照删除、恢复等核心管理能力被安全守卫误阻断）
- 测试游戏：R.E.P.O.
- 当前目录身份：
  - 目录/目录站标识：`repo`
  - 本地安装实例 ID：`gi_6273536933cf3fe589be`
- 现象：
  1. `snapshot_list` 能正确列出当前 R.E.P.O. 的 15 个快照；
  2. 对其中任意快照执行 `snapshot_delete` 时，均提示快照属于
     `gi_6273536933cf3fe589be`、当前游戏是 `repo`，并以“跨游戏删除”为由拒绝；
  3. 重新执行 `scan_games` 后仍然复现。
- 已确认根因：
  - 快照创建和数据库存储已经采用本地安装实例 ID；
  - `snapshot_list` 经过 `game_storage_id(...)`，能把 `repo` 映射到当前实例；
  - `snapshot_delete` / `snapshot_restore` 的跨游戏守卫仍直接用数据库中的
    `gi_*` 与原始目录标识 `repo` 比较，导致同一游戏的两个身份表示被判为不同游戏。
- 数据安全结论：
  - 本次为安全守卫假阳性，快照没有被删除，也没有改动游戏文件；
  - 不得通过关闭跨游戏守卫来规避，必须统一身份解析后再比较。
- 修复要求：
  1. 列表、预览、删除、恢复统一使用 `game_storage_id(cfg, cfg.game_slug)`；
  2. 快照操作按安装实例隔离，不能退回仅用目录 slug；
  3. 错误提示同时显示用户可读游戏名和安装路径，不直接暴露 `gi_*` 作为游戏名；
  4. 增加 `game_slug=repo`、`game_instance_id=gi_*` 的同游戏删除/恢复回归测试；
  5. 保留真正跨安装目录操作的拒绝测试。

## BT-SEARCH-GITHUB-08：GitHub 搜索缺少当前游戏相关性门槛

- 记录时间：2026-07-29
- 严重级别：P1（推荐质量、来源可信度和误安装风险）
- 测试游戏：《超级兔子人》
- 现象：智能推荐返回 5 个 GitHub 候选，但均与当前游戏无可靠关系，包括：
  - OpenWrt 自动生成的 `.config`；
  - `skyfactory-2.4-faults`、`skyfactory-2.4` 启动日志；
  - GIANTS Engine 日志仓库；
  - `Graph-of-energy-cells` 棋盘/算法项目。
- 问题性质：
  - 当前 GitHub 查询更接近“关键词全文检索”，没有证明仓库是当前游戏 Mod；
  - 通用词、中文翻译词、日志内容、配置文件内容命中后，被直接提升为 Mod 候选；
  - 搜索摘要经过模型润色后看起来像“功能介绍”，但没有游戏身份、Mod 加载器或安装结构证据；
  - “详情待核验”只能阻止立即安装，不能使明显无关结果进入推荐决策表。
- 搜索策略要求：
  1. GitHub 结果进入推荐表前必须满足至少一项强游戏证据：
     游戏正式名/稳定别名出现在仓库名、描述、主题、README 或 Release 中；
  2. 同时至少满足一项 Mod 证据：
     当前游戏加载器、明确 Mod 安装说明、可用 Release 资产、manifest/插件入口或可信来源反链；
  3. 仅代码内容、日志、`.config`、通用 `utils`、教学项目命中不得作为推荐候选；
  4. 游戏名歧义时使用短语搜索和平台/加载器限定，不允许拆成宽泛单词后全局召回；
  5. GitHub 应作为补充来源；存在该游戏的 Steam Workshop、Thunderstore 或 Nexus 时优先专站；
  6. 核验失败或游戏不匹配的结果应从推荐表移除，而不是继续显示为“待详情核验”；
  7. 搜索结果为空时如实报告，不得用跨游戏仓库凑满候选数量。
- 验收条件：
  - 用同一“超级兔子人 Mod 推荐”请求回归时，上述 5 个仓库召回数必须为 0；
  - 每个保留的 GitHub 候选必须可展示“游戏证据”和“Mod/安装证据”；
  - 找不到可靠 GitHub Mod 时，结果允许为空并说明建议查看的专用来源。

## BT-SEARCH-SOURCE-09：多来源覆盖不完整且跳过原因不可见

- 记录时间：2026-07-29
- 严重级别：P1（开放多源定位与用户信任）
- 测试游戏：《超级兔子人》
- 用户请求：查找扩展 Mod。
- 实际工具调用：
  - 已调用：`mod_recommend`、`workshop_search`、`github_search`；
  - 未调用：`thunderstore_search`、`nexus_search`、GameBanana 搜索。
- 当前无法从界面判断：
  - 这些来源确实不收录该游戏；
  - 游戏名称/社区 slug 没有映射成功；
  - 来源适配器不可用；
  - Agent 路由策略主动跳过；
  - 或者只是搜索流程提前结束。
- 问题性质：
  - “没有结果”与“根本没有搜索”是两种不同结论；
  - 对外主打多源开放适配时，静默跳过来源会让用户误以为已经完整检索；
  - 盲目强制搜索所有来源同样不合理：不存在对应游戏社区时只会增加延迟和噪声。
- 修复要求：
  1. 搜索前建立当前游戏的来源能力矩阵：支持、未映射、不收录、暂不可用、用户未配置；
  2. 只搜索有有效游戏映射的来源，但在结果中逐项显示已搜索/跳过及原因；
  3. 对未知游戏先执行轻量来源发现，不直接用宽泛 GitHub 全局搜索兜底；
  4. 专站无结果时明确显示“已搜索但结果为空”，不得等价为“该游戏没有 Mod”；
  5. GitHub 只能补充可靠候选，不能替代未执行的专站搜索；
  6. 最终报告显示来源覆盖率，例如“已核查 2/5；2 个无社区映射；1 个未配置”。
- 验收条件：
  - 同一请求中，用户能看到 Workshop、Thunderstore、Nexus、GameBanana、GitHub
    每个来源的实际状态；
  - 未调用某来源时必须有机器可验证的跳过原因；
  - 不再把“只搜了 Workshop/GitHub”表述成完整多源检索。

## PRODUCT-EXPLORE-01：模组“逛超市”探索模式（暂不自建全量服务）

- 产品判断：这是有价值的独立体验，但不是当前核心安装链路的发布阻断项。
- 用户价值：通过配图、中文简介、标签、热度、更新时间和兼容性浏览 Mod，
  能保留发现与挑选的乐趣，而不必每次先组织精确提示词。
- 当前不采用：
  - 自建全市场镜像；
  - 集中保存全部 Mod 文件与配图；
  - 为追求“全收录”立即租用服务器和维护爬虫集群。
- 推荐的低成本阶段：
  1. 增加“探索”入口，按当前游戏按需请求各来源；
  2. 只在本机缓存来源允许使用的元数据、缩略图 URL 和用户已浏览条目；
  3. 用来源适配器统一卡片结构，下载仍回到原来源或现有安装链路；
  4. 对无法取得图片或详情的来源如实降级，不伪造完整商城体验；
  5. 等真实用户量和请求量证明有必要后，再评估服务端索引、增量同步与 CDN。

## BT-INVENTORY-PACKAGE-11：一个下载包的多个服装变体被重复计为独立 Mod

- 记录时间：2026-07-29
- 严重级别：P1（管理数量失真，并可能诱导用户逐个更新、禁用或卸载不可独立管理的文件）
- 实机证据：剑星页面显示 105 个 Mod；数据库中实际为 50 个由 ModAgent 安装的上游包，加上 55 个扫描器从这些包内部再次识别出的服装变体。
- 产品语义：
  - 一个上游下载包、一次安装事务、一个来源版本，应当对应一个可管理 Mod 包；
  - 包内 `.pak/.utoc/.ucas` 变体可以作为说明信息展示，但不能拥有独立的更新、启用、禁用和卸载生命周期；
  - 管理动作必须作用于完整上游包，避免只操作三件套中的一部分。
- 本轮修复：
  1. 扫描器发现候选文件完全属于已登记上游包时，不再导入新的独立 Mod；
  2. 历史 `imported` 记录的完整文件集若是唯一上游包的严格子集，只合并数据库别名，不删除、不移动任何游戏文件；
  3. 若同一子集可能属于多个包，保持原记录并要求后续人工核验，不做激进去重；
  4. API 与界面按“Mod 包”计数，并可显示“包内 N 个变体”；
  5. 更新、启用、禁用和卸载继续以完整包文件清单为边界。

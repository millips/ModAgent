## BT-UPDATE-01：已安装 Mod 身份推断错误

- 严重级别：P0（错误更新对象可能覆盖用户文件）
- 用户意图：更新当前已安装的 `Auto Forager`。
- 搜索候选：
  - Nexus #7736：`Auto Forager (previously Auto Shaker)`
  - Nexus #47161：`AutoForager`
- 本机事实：测试用户确认实际安装来源是 **Nexus #7736**。
- 错误表现：Agent 根据名称、作者/日志线索推测安装项更像 #47161，并要求用户二选一；该推测与本机事实不符。
- 初步原因：
  1. 本地数据库使用 `local_*` 哈希身份，未保存或未恢复可靠的 Nexus 来源绑定。
  2. 两个候选名称高度相似，名称模糊匹配不能证明来源身份。
  3. SMAPI `manifest.json` 的 `UniqueID`、作者、版本没有与 Nexus 详情形成确定映射。
  4. 当前对话层可能把日志/分类线索当成来源证明。
- 安全要求：
  - 无稳定来源绑定时不得宣布“安装的是某个 Nexus ID”。
  - 更新前必须以本地 manifest、历史安装账本、已验证来源绑定或包内指纹完成身份确认。
  - 两个候选均可能匹配时只能报告“身份未确认”，不得用作者/名称近似度替代证明。
  - 用户明确提供 Nexus ID 后，应写入经过确认的手动绑定，并在后续更新中复用。
- 验收条件：
  - 给定本地 #7736 的 manifest/文件指纹，更新检查稳定选中 #7736。
  - #47161 即使名称更接近，也不能覆盖已有的确定绑定。
  - 身份未确认时更新按钮不可执行，只允许查看候选和补充绑定。

## BT-UPDATE-03：Stardew Valley 更新错误落入 BepInEx

- 严重级别：P0（更新后 Mod 实际失效，禁止按当前候选发行）
- 已确认现场：
  - `Mods/AutoForager自动觅食` 只剩 `i18n/`，没有主 DLL；
  - `BepInEx/plugins/7736_Auto_Forager_(previously_Auto_Shaker_)` 包含 `AutoForager.dll` 和 `i18n/`；
  - Stardew Valley 使用 SMAPI，只加载游戏根目录下的 `Mods/`，不会从该 BepInEx 路径加载此 Mod。
- 已确认代码根因：
  1. `installer.GAME_LAYOUTS` 没有 `stardewvalley`；
  2. Stardew 专项代码目前只覆盖 SMAPI 状态验收和压缩包依赖预检，没有定义安装落位；
  3. `mod_update` 卸载旧版后直接调用通用 `installer.install_mod(...)`；
  4. 通用安装器把未匹配的散 DLL 兜底到 `BepInEx/plugins/<包名>/`。
- 当前测试机处置：
  - 对“卸载两个残留并重新下载”的确认问题选择 **n**；
  - 当前版本重新下载后仍会走同一错误落位，不能解决问题；
  - 保留现场或先备份，待修复版使用 SMAPI 专项迁移/修复流程。
- 必须实施：
  - 增加 Stardew/SMAPI 安装布局：完整 Mod 文件夹必须落入 `Mods/<mod-folder>/`；
  - 以 `manifest.json` 作为 SMAPI Mod 根目录的强证据，保持 DLL、`i18n/`、内容包及其他同级文件在同一目录；
  - 禁止 Stardew 的普通 Mod 使用 BepInEx 散 DLL 兜底；
  - `mod_update` 安装后必须调用 `stardew_smapi_status` 或等价本地验收，确认目标 manifest 与 DLL 位于 `Mods/`；
  - 更新失败或落位错误时必须恢复旧版本，不能只以“文件已复制”判定成功；
  - 增加从错误 `BepInEx/plugins/...` 路径迁回 `Mods/` 的一次性修复流程，并同步数据库绝对路径。
- 回归用例：
  - #7736 更新包包含 `manifest.json`、`AutoForager.dll`、`i18n/` 时，三者必须落在同一个 `Mods/<folder>/`；
  - 更新完成后 `BepInEx/plugins/` 不得新增 #7736 文件；
  - SMAPI manifest 扫描必须能识别更新后的 UniqueID 与版本；
  - 旧目录清理、数据库 `files_installed`、卸载预览和快照均指向新路径。

## BT-UPDATE-02：歧义候选介绍不完整

- 严重级别：P1
- 表现：搜索返回 #7736 与 #47161 两项，但只给出短功能概括、作者、版本和下载量，缺少足以判断的完整信息。
- 缺少的信息：
  - 两项分别适用的游戏/SMAPI 版本；
  - manifest `UniqueID`；
  - 主要功能差异；
  - 前置依赖与安装结构；
  - 是否为继任、分支或同名不同项目；
  - 本机版本与候选版本的逐项证据对照。
- 验收条件：
  - 更新候选必须逐项进入详情页核验。
  - 两个候选都要输出完整中文简介，不能只完整介绍其中一个。
  - 决策区必须显示“本机证据 / 候选证据 / 一致项 / 冲突项 / 尚未确认项”。

## BT-I18N-01：Mod 管理界面缺少中文名与中文简介

- 严重级别：P1（可用性）
- 当前表现：管理页主要显示英文 Mod 名，第二行仅显示内部 ID；普通中文用户无法快速理解用途。
- 已确认实现缺口：前端已经预留 `name_cn` 和 `desc` 展示位，但 `/mods` 接口没有返回对应元数据，前端目前把 `name_cn` 设成英文原名、把 `desc` 固定成内部 ID。
- 目标展示：
  - 主标题：中文参考名；
  - 副标题：来源英文原名；
  - 简介：基于来源详情、manifest 或 README 的中文功能简介；
  - 身份：来源平台与稳定 ID 单独显示，不能被中文名替代。
- 数据原则：
  - 中文名只是显示别名，不参与下载、更新、卸载和依赖匹配。
  - 没有详情证据时不根据标题猜功能；显示“简介待核验”。
  - 翻译结果需要持久化，避免每次打开管理页重复调用模型或产生不同译名。

## BT-FOLDER-01：物理 Mod 文件夹中文化

- 严重级别：P1（需要安全设计，不能直接照搬手工改名）
- 测试者效果：例如 `AutoForager自动觅食`，在资源管理器中可读性很好。
- 当前风险：
  - `installed_mods.files_installed` 保存绝对路径，外部重命名会使账本失效；
  - 更新可能在原始英文目录重新解压，形成两个同时加载的副本；
  - 卸载、禁用、依赖检查和快照可能漏掉改名后的文件；
  - 部分加载器、整合包或脚本可能依赖原目录结构。
- 当前决策：**不默认重命名现有真实 Mod 目录。**
- 推荐方案：
  1. 第一阶段先完成管理界面的中文名与中文简介，不改磁盘路径。
  2. 如需资源管理器可读性，设计“受管中文别名”功能：仅处理 ModAgent 新安装且通过加载器专项验证的目录。
  3. 重命名必须作为事务执行：更新数据库全部路径、来源绑定和快照域；失败自动回滚。
  4. 更新前用稳定 ID/manifest `UniqueID` 找目录，不再依赖文件夹名。
  5. 对现有用户手工改名目录先重新扫描并对账，不直接二次改名。

## 新确认的未解决问题：共享密钥

真实 Electron 假密钥实验：A 加密成功、A 重启解密成功、独立 B 解密失败；隔离 C 仅使用 A 的加密上下文后成功。

因此仅共享 credentials-v2.json 不足以跨 Free/P 或 r3/r4 配置使用，密文还依赖原配置的加密上下文。与 [Electron 官方问题记录](https://github.com/electron/electron/issues/39733) 一致。

证据：build/conversation-flow-20260906-r4/cross-profile-credentials.json，product_cross_profile_acceptance=false。

没有覆盖、删除或重新加密真实凭据。为完成授权的 API 测试，仅在临时隔离配置复用了原配置的 Windows 加密上下文，没有复制聊天、Cookie、游戏清单或明文密钥。**这不是产品修复，r4 仍可能要求首次配置。**

后续应采用稳定的受保护凭据服务或直接 Windows 用户级保护，提供安全的旧密文迁移；不能共享整个用户配置目录来绕过隔离。

代码复核还发现 load() 先读取共享密文，失败即抛错，尚未尝试当前配置自己的本地密钥。修复时须同时区分“共享凭据不可读”与“本地凭据不可用”，不能把一个来源失败扩大成所有凭据不可用，也不能静默覆盖坏密文。

该分支已由 electron/scripts/test-r4-local-credential-fallback.cjs 独立复现：无共享密文时本地假密钥正常加载；添加其他配置密文后抛出 credential_store_unreadable，本地有效密钥无法加载，测试退出码 1。仅使用临时目录和假密钥，没有读取真实凭据。

# ModAgent Agent Core v2 系统审计报告

检查日期：2026-09-05。整理交付：2026-09-06。
范围：当前工作区源码及隔离回归，不是对旧安装包或用户真实游戏目录的验收。
基准提交：db05cce0；工作区存在大量既有未提交修改，本报告以检查时的工作区为准。

## 一、结论

你的担心有事实依据。当前问题不只是提示词过长，而是“旧的大型 Agent 流程 + 新的任务控制层 + 多处重复门禁 + 不完整的恢复机制”同时存在。

Agent Core v2 已经有任务类型、短提示词、工具白名单、数据库表、事件和卡片，但它还不是计划中独立、可恢复、以证据判定完成的执行系统。更准确的定位是：**部分实现的迁移骨架，仍由旧循环承担主要编排。**

不能据此断言整个项目应该推倒重写。安装事务、路径边界、确认预检、来源适配器、推荐组件已有可复用成果；最需要治理的是它们之间的任务、权限、结果和生命周期契约。

本次复现的多个问题不需要真实 LLM 就能触发，因此不能把这些缺陷归咎于模型。模型自身对真实提问的理解质量，本次没有联网评测，不能量化其贡献。

## 四、主要发现

### 01. 意图判断可以误发更新权限——发布阻断风险，已离线复现

输入“不要帮我更新，我只是想知道全部更新是什么意思”，路由结果为 UPDATE_INSTALLED，置信度 0.98，install_authorized=true，并开放 mod_update。

根因：正则检测到了“帮我更新/全部更新”，没有处理否定、引用和解释语境。所谓置信度是规则中写死的数值，并非经过校准的理解可靠度。

这证明授权判断存在缺陷；不等于已经在真实用户电脑完成了误更新。后续工具检查是否拦下具体请求，仍需链路测试。授权层本身不能依赖后层偶然救场。

其他实测：

| 用户表达 | 当前路由 |
|---|---|
| 为什么检查更新会失败？先别更新 | UPDATE_INSTALLED，未进入诊断 |
| 分享码是什么意思？ | IMPORT_SHARE，未进入解释 |
| 推荐一个能改钱的 mod，不要别的功能 | RECOMMEND_BROAD |
| 有哪些 eve 的换皮但是是别的游戏动漫 IP，比如 FF7 Tifa | CHAT_EXPLAIN，工具为空 |
| 禁用我选中的这个 mod | CHAT_EXPLAIN，工具为空 |

结构化分类器只有可选接口，API 调用路由时没有传入实际分类器，也没有把多轮上下文交给它。换模型无法修复发生在模型调用之前的这些路由错误。

证据：[路由器](<I:/工作/项目/模组agent/modagent/orchestration/router.py:85>)；[API 路由调用](<I:/工作/项目/模组agent/modagent/api.py:958>)。

### 02. 新旧工具门禁互相打架——P1，已捕获实际请求

v2 为 RESOLVE_SOURCE 定义了详情和来源工具，但旧 Agent 又用另一份列表过滤。最终“补齐详情”发给模型的工具只剩：

- nexus_get_detail
- game_file_check

因此，GitHub/GameBanana 等条目无法借这条路径正常读取来源页或 README。追加指令又要求核验依赖、必要时精确搜索，但后面的代码继续禁用搜索。

“创建一个快照”正确路由为 SNAPSHOT_ROLLBACK，却因为没有 install 授权而移除了 snapshot_create；模型拿不到创建工具。

这是政策组合错误，不是模型不听话。只保留“禁止做什么”的测试，检不出“该做的事也做不了”。

证据：[v2 权限](<I:/工作/项目/模组agent/modagent/orchestration/policies.py:59>)；[旧过滤](<I:/工作/项目/模组agent/modagent/agent.py:2246>)；[追加选择规则](<I:/工作/项目/模组agent/modagent/agent.py:2383>)。

### 03. 失败会被标记成功，甚至断流后也如此——P1，已复现

离线结果：

- 只有一次失败搜索，回复“搜索失败，请稍后重试”：保存 status=completed、retryable=false。
- 没有任何证据、没有文本：补成“本轮任务已完成”。
- 模拟流式响应先返回一点文字再抛 TimeoutError：最终数据库仍记录 completed。

根因：

1. finalize_from_text 用“是否有文本”参与成功判断，而不是目标是否完成。
2. chat_stream 的 finally 先自动完成任务。
3. API 随后的异常处理调用 fail，但 runtime 已经 finished，不再接受失败状态。

这直接违反“每轮有真实终态”的目标；加一张终态卡片并不能保证卡片内容真实。

证据：[结果判定](<I:/工作/项目/模组agent/modagent/orchestration/runtime.py:202>)；[提前终结](<I:/工作/项目/模组agent/modagent/agent.py:3044>)；[异常处理](<I:/工作/项目/模组agent/modagent/api.py:1072>)。

### 04. 防重复执行账本不具备正确业务身份——P1，已复现

当前幂等键取参数里第一个可用身份，而非组合完整身份：

- 同一 mod_id=390、不同 file_id=11/12，得到同一个键。
- 两次不同内容的 batch_download，都会落到 target=task，得到同一个键。
- 等待用户登录的 manual_action_required 被旧层视为非错误，新账本便将下载记录为已完成。

后果可能是：第二个变体被跳过、未完成下载被误当成完成、恢复复用了错误结果。

此外，账本只在操作返回后登记，没有执行前原子占位及崩溃后核对。“写盘成功但记账前退出”的窗口仍在；这是静态确认的恢复风险，本次未用真实安装复现。

证据：[账本入口](<I:/工作/项目/模组agent/modagent/orchestration/runtime.py:104>)；[身份取值](<I:/工作/项目/模组agent/modagent/orchestration/runtime.py:259>)；[人工门禁结果分类](<I:/工作/项目/模组agent/modagent/agent.py:1396>)。

### 05. 恢复了任务记录，没有完整恢复执行上下文——发布阻断风险，静态链路确认并有门禁隔离复现

恢复 API 从旧记录取回 intent、targets 和 authorization，但调用 Agent 时仍传入这次新请求的 recommendation_selection 和 selection_action。前端“继续未完成项”只发送 resume_task_id，没有重带原来的选择。

旧 Agent 的目标门禁依赖 _selection_action 等临时字段，而不是统一检查 TaskSpec.targets。离线测试中，TaskSpec 只允许 Mod 42，缺少旧选择字段时，对 Mod 999 的下载调用仍到达模拟执行器。

因此恢复任务可能失去原目标约束。检查点只是“工具名+完整参数”的缓存；模型改一下参数就不命中。成功步骤重用也不能等同于恢复一个明确的执行阶段。

这是“TaskSpec 有记录”和“TaskSpec 是执行事实来源”之间的缺口。本次没有真实下载目标 999。

证据：[恢复规格](<I:/工作/项目/模组agent/modagent/api.py:979>)；[转发请求](<I:/工作/项目/模组agent/modagent/api.py:1054>)；[前端恢复](<I:/工作/项目/模组agent/electron/src/components/ChatPage.jsx:1451>)；[旧身份门禁](<I:/工作/项目/模组agent/modagent/agent.py:1019>)。

### 06. 取消、超时和真实执行不是同一个生命周期——发布阻断风险

已复现两件事：

- runtime.cancel 之后继续调用 tool_finished，仍追加 tool_finished 事件并写检查点。
- 将工具超时缩短为 0.03 秒，执行器已返回“超时、已跳过”，模拟工作线程仍存活，随后完成模拟副作用。

当前取消有真实保护：新轮次独立 Agent、会话事件过滤、部分下载循环的取消检查、旧历史写回过滤。不能说完全没有取消机制。

但线程池不能通过停止等待来终止已经运行的函数。安装事务和快照文件循环没有统一接入任务取消/写入许可；停止按钮与底层提交之间仍需明确安全边界。

实际游戏是否会在某个具体取消场景继续写入，本次没有用真实文件验证；模拟结果证明执行器没有提供该保证。正确处理应是停止新增工作、在安全提交点收尾并如实报告，而非提前声称全部停止。

证据：[工具等待与超时](<I:/工作/项目/模组agent/modagent/agent.py:1213>)；[runtime 后续写入](<I:/工作/项目/模组agent/modagent/orchestration/runtime.py:104>)；[事务提交](<I:/工作/项目/模组agent/modagent/installer.py:91>)。

### 07. shadow 并非纯观察——P1，已复现

_exec 只要存在 runtime，就会读取完成账本并跳过执行，没有要求 feature_mode=on。

在 shadow 中，用同一压缩包、不同工具显示名称调用两次 tool_extract，模拟执行器只被调用一次，第二次返回 reused_effect=true。

影子模式会改变行为，因此不能将其当成无干扰的新旧对照实验。开关存在，不代表灰度机制已经验收。

证据：[无条件复用](<I:/工作/项目/模组agent/modagent/agent.py:1190>)。

### 08. 搜索相关性仍是弱关键词匹配——P1，已复现

当前过滤对英文关键词采用“命中任意一个词即可”，纯中文提问没有可提取英文词时直接放行。

离线结果：

- 查询 EVE Tifa，EVE Makeup 通过过滤。
- 查询“蒂法换皮”，Fast Intro 通过该过滤函数。
- GitHub 仓库名为 money-mod，所有者为 DemonologistFan，说明明确是 Zanzarah 的项目，仍通过 GitHub 游戏匹配。
- 把显式标记为 zanzarah 的 money 候选交给中央推荐转换器，当前游戏为 Demonologist，仍输出 1 个候选。

前两条是函数级过滤验证，第四条是模拟错误来源数据，不代表实际网站必定返回这些数据。但它们证明缺少独立的游戏身份+目标功能双重硬门禁。

作者字段虽然已经从功能匹配中移除，full_name 和 URL 仍含所有者名称。过滤主要对模型实际发出的查询负责；若模型已经把目标改歪，没有独立 QueryPlan 锁住原始语义再验收。

证据：[查询匹配](<I:/工作/项目/模组agent/modagent/recommendation_ui.py:993>)；[推荐转换](<I:/工作/项目/模组agent/modagent/recommendation_ui.py:1033>)；[GitHub 游戏证据](<I:/工作/项目/模组agent/modagent/sources/github.py:47>)。

### 09. 搜索预算不是来源请求预算，慢来源仍拖住整体——P1，静态确认

8 次预算统计的是 Agent 工具调用。一次 mod_recommend 可并发请求最多 5 个来源，来源内部还有刷新和重试，因此不能宣称最多 8 次来源请求。

搜索工具在 _exec 中没有总超时；聚合器等待所有 future 才返回。虽保存了成功来源结果，但没有把每个已完成来源的候选实时交付给界面。某个来源极慢时，用户仍可能只看到等待。

尚未实现计划中“3 个高置信候选/10 个可展示候选即停止”的统一判定。

证据：[预算](<I:/工作/项目/模组agent/modagent/agent.py:855>)；[聚合等待](<I:/工作/项目/模组agent/modagent/tools.py:4528>)。

### 10. 有 SSE，不等于自然语言流式反馈——P1，静态确认

_consume_stream 把完整模型响应读完才返回。文字回复最后一次性发送；工具前模型草稿默认缓冲。已有固定 progress 和 10 秒 heartbeat，这是进步，但不是边生成边显示答案。

更重要的是，正常 SSE 分支能处理 task_event，applyRecoveredEvents 分支没有同样的处理。刷新后的任务恢复可能漏掉新终态卡；界面主要恢复入口又基于内存任务，而不是持久任务表。

后台重启后，持久任务可能仍是执行中，但没有查到统一的启动核对、标记中断和恢复选择流程。前端也未把任务事件序号作为完整的消费去重契约。

证据：[模型流缓冲](<I:/工作/项目/模组agent/modagent/agent.py:1825>)；[恢复分支](<I:/工作/项目/模组agent/electron/src/components/ChatPage.jsx:694>)；[正常分支](<I:/工作/项目/模组agent/electron/src/components/ChatPage.jsx:1265>)。

### 11. 网络策略分散，证书验证存在明确问题——P1

好的部分：官方合集已有 Raw → GitHub API → GitHub 文件端点的回退；下载有断点续传、失败分类和部分取消检查。

缺口：

- 来源重试器将 urllib HTTPError 当作 URLError 瞬时错误，401/403/404 在离线分类中都返回可重试。
- 新的 2 次来源重试和旧下载最多 12 轮尝试、120 秒单请求超时等并存，缺少任务统一时间预算。
- LLM 的 HTTPX 路由、urllib 来源请求和浏览器连接不是同一套代理路径。
- Nexus API 以及下载代码直接使用未验证证书的 SSL context。API 请求还携带密钥，不能把关闭证书校验当作正常网络修复。

没有证据表明已发生窃听或恶意下载；这里确认的是安全配置缺陷。今天 Codex 本身的连接中断，也不能用 ModAgent 源码来归因。

证据：[来源重试](<I:/工作/项目/模组agent/modagent/tools.py:49>)；[Nexus 请求](<I:/工作/项目/模组agent/modagent/nexus.py:186>)；[下载请求](<I:/工作/项目/模组agent/modagent/downloader.py:1521>)；[LLM 路由](<I:/工作/项目/模组agent/modagent/networking.py:17>)。

### 12. 变体有局部修复，但没有贯穿全流程的身份模型——P1/P2

界面确实有变体下拉，推荐转换也有 variants。扫描器对剑星使用至少 3 个成员、文件名前 3 个英文数字词相同的归组规则。

这能处理部分 Addon_Nier_03 场景，却无法证明任意同前缀文件属于同一 Mod，也无法覆盖两个变体、跨目录组件、多个可共存类别。

当前界面按每个 selection_key 保存一个 variant_id；不能把“已有一个下拉框”当成“一个 Mod 家族下多个兼容组件、多组选项和互斥关系已经建模”。下载和账本又采用不同身份粒度，见发现 04。

应区分：来源项目、发行版本、下载文件、安装实例、可选组件、互斥组。列表聚合不能自动等同于卸载范围合并。

证据：[变体 UI](<I:/工作/项目/模组agent/electron/src/components/RecommendationDecisionTable.jsx:55>)；[本地归组](<I:/工作/项目/模组agent/modagent/scanner.py:670>)。

### 13. 状态机更多是在记录旧流程，而非驱动流程——架构缺口

枚举包含 EXECUTING 和 VERIFYING，但当前生产调用中没有发现把任务推进到这两种状态的实际调用；通常是开始、收集、直接终结。finish 也绕开 transition 的合法转换校验。

TaskSpec 虽是 frozen dataclass，内部字典仍可修改，离线验证可直接修改 authorization。事件不携带 turn_id；同 task_id 恢复会覆盖规格中的轮次，晚到的旧回调仍需额外防护。

另外 /chat 和 /debug/replay 仍调用旧 chat，不走 v2 stream 的规格和策略。即使打开 on，也不能说所有入口都受同一核心控制。

证据：[状态实现](<I:/工作/项目/模组agent/modagent/orchestration/runtime.py:72>)；[规格结构](<I:/工作/项目/模组agent/modagent/orchestration/models.py:53>)；[旧接口](<I:/工作/项目/模组agent/modagent/api.py:895>)。

### 14. 只读的含义不统一——P2，静态确认

mod_source_align 没有被 MUTATING_TOOLS 正确覆盖，某些只读模式允许调用它；实际实现会新增、更新或删除来源绑定。

这主要是管理数据库元数据变更，不等同于写游戏文件，但它意味着“只读”现在不是清晰、可验证的权限契约。应分别定义只读查询、缓存写入、来源绑定和游戏副作用。

证据：[权限表](<I:/工作/项目/模组agent/modagent/orchestration/policies.py:42>)；[来源对齐](<I:/工作/项目/模组agent/modagent/tools.py:3423>)；[绑定写入](<I:/工作/项目/模组agent/modagent/source_alignment.py:274>)。

## 五、为什么测试全过，问题还在

本次原有 120/120、1000/1000 确实通过，不是虚构。但测试范围与计划要求差距很大：

- runner 主要检查路由类型，以及指定的禁止工具是否出现在允许列表。
- 不调用真实模型，不检查自然语言答复，不验证事实证据或最终状态。
- mutation_allowed 字段没有被 runner 用于实际写入断言。
- 500/1000 主要是在原有句子前后加“请问”“当前游戏已经选好”等包装，不是 1000 条独立业务场景。
- 没有实现计划中的固定工具返回、真实多轮故障、模型 3 次重复和发布门槛完整评测。
- 当前新增 v2 单元测试只有 12 个，主要是正向路径。
- 取消测试证明了“已经取消后不再开始新调用”等局部性质，没有证明所有在途副作用停止。
- 相关性回归覆盖了原来的少数错误样例，但没有覆盖共享人物词、中文过滤空缺、所有者污染等邻近情况。

本次在这些测试通过的同时复现了前述缺陷。这不是说原测试没价值，而是不能把其通过率命名为“Agent 整体正确率”。

证据：[评测执行器](<I:/工作/项目/模组agent/evals/runner.py:15>)；[扩展方式](<I:/工作/项目/模组agent/evals/variants.py:8>)；[v2 测试](<I:/工作/项目/模组agent/tests/test_agent_core_v2.py>)。

## 七、哪些值得保留，接下来先处理什么

值得保留：安装预检和事务回滚、路径边界、两阶段确认基础、下载缓存与部分重试、来源适配器、推荐与变体组件、会话取消的已有隔离措施，以及现有回归测试。

建议处理顺序（本轮未实施）：

1. 先把发现 01、03、04、05、06、07 变成独立失败测试：否定授权、真实终态、完整操作身份、恢复目标、在途取消和纯影子模式。
2. 明确一个唯一 TaskSpec/确认计划作为执行依据；旧临时选择字段不能成为更权威的授权源。
3. 把结果统一为完成、部分、等待用户、失败、取消，不能再用单个 ok 布尔值把“登录中”与“已下载”混为一谈。
4. 对已经迁移的模式移除重复旧门禁，补上功能可达性测试，再迁移下一个模式。
5. 建立原始目标和游戏身份的独立证据校验，修复搜索后再进行真实模型对比。
6. 拆分回复生成、工具执行、事件消费；依据结构化事实压缩上下文，再删除已被代码承接的提示词。
7. 恢复执行及副作用测试通过后，才谈默认开启和新包发布。

不建议现在再追加一大段提示词、只换模型赌效果，或在没有行为基线的情况下集中重写。也不建议把现有所有保护直接删掉：应先证明替代机制能承接其职责。
